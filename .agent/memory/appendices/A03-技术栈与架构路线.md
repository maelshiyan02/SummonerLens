# A03 · 技术栈与架构路线

> 上级索引：`MEMORY.md` §1（A03）｜触发时机：选型、搭骨架、写代码之前｜相关：A01 定位、A04 统计

## 1. 推荐技术栈（本地优先 + 用户储备匹配）

| 层 | 选型 | 可行性 | 理由 |
|---|---|---|---|
| **界面壳** | **Flutter Desktop（Windows）** | ✅ 高 | 用户主技能；Flutter 3.x Windows 稳定 |
| **数据层** | **Python**（pandas / polars / duckdb） | ✅ 高 | 用户已用 Python 做 Mangrove 工具 |
| **统计/建模** | Python（scipy / numpy / ELO 自写） | ✅ 高 | Wilson 区间、ELO/MMR、聚类都在生态内 |
| **可视化** | **ECharts**（前端/webview）或 **pyecharts**（Python） | ✅ 高 | 见 §3 许可 |
| **界面↔数据桥** | Flutter 调本地 Python（subprocess / 本地 FastAPI） | ✅ 中 | 常见模式，Mangrove 已验证 headless 调用 |

**结论**：最自然组合 = **Flutter Desktop 壳 + Python 数据/统计层 + ECharts 可视化**。纯 Python（PySide6 + QWebEngine + ECharts）也可，但偏离用户主技能，不优先。

## 2. 本地优先架构取向

- 不建公网服务、不做账号系统、不做实时查库。
- 数据在本地落库（SQLite / DuckDB / Parquet）；统计与建模在本地跑（Python 脚本或本地 FastAPI）。
- 界面是**本地桌面应用**，打开即用、可离线。
- 与 resg「数据即 ES module + SW」思路一致（零后端、可离线），但更进一步：分析也在本地，不依赖任何远端计算。

## 3. 可视化选型（许可敏感）

**三家 BI/大屏工具最终都靠 ECharts 渲染 ⇒ 真正吸收的是 Apache ECharts，其余仅借鉴思路：**

| 项目 | 定位 | 许可 | 可借鉴点 | 警告 |
|---|---|---|---|---|
| **Apache ECharts** | 图表引擎（TS） | **Apache-2.0** | 直接用（webview / pyecharts） | 无，放心用 |
| **pyecharts** | ECharts 的 Python 封装 | MIT | Python 层直接出图 | 无 |
| **DataEase** | 开源 BI（Vue+Spring+ECharts） | **GPLv3（传染）** | 借鉴「数据源→数据集→图表→仪表板」组织 | **勿复制代码** |
| **Cola-Designer** | Vue2 大屏设计器 | **GPL-2.0（传染）** | 借鉴三栏大屏构图 | 作者已停更；**勿复制代码** |
| makeapie 镜像 | ECharts 实例画廊 | — | 抄 option 配置写法 | 只学配置，不爬数据 |

> 一句话：可视化内核 = **ECharts（前端/webview）或 pyecharts（Python）**，无许可风险；DataEase/Cola-Designer 只学布局交互思路。

## 4. UI 地基

- **原则**：借思路不抄界面。两站（hexdata/resg）交互可吸收：分段筛选器、英雄别名词典搜索、跨版本趋势图、深色默认主题、自动刷新。
- **落地路径**：
  ```
  Flutter Desktop（Windows）主壳
     ├─ 导航 / 筛选器 / 英雄别名词典搜索（自写）
     ├─ 图表区：webview 嵌入 ECharts
     └─ 数据桥：调本地 Python（pandas/polars + scipy + pyecharts 预渲染）
  本地数据层：DuckDB/SQLite + Python 统计脚本（Wilson/ELO/MMR）
  ```
