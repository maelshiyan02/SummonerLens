## 五、数据来源与腾讯 API 追溯（本轮第 1、7 点）

### 5.1 三家数据源，两个层次（保留）

- **层次一·对局统计**：两家都**自建样本**（百万场量级，例：亚索 1,829,755 场），不来自 Riot 官方统计。
- **层次二·静态元数据**：Data Dragon（名称/图标）+ CommunityDragon（强化符文名称/图标，Data Dragon 没有）。

### 5.2 腾讯数据 API 追溯（本轮核实：用户宣传者说法属实）

用户提到"hexdata 宣传者说数据可追溯到腾讯相关 API"——**属实，路径如下**：

| 接口 | 端点 | 说明 |
|---|---|---|
| 战报 | `https://www.wegame.com.cn/api/v1/wegame.pallas.game.LolBattle/GetBattleReport` | 按召唤师查段位/各赛季数据 |
| 对局列表 | `https://m.wegame.com.cn/api/trpc/Proxy/Forward/.../GetBattleList` | 按 id+大区查最近对局 |
| 对局详情 | `.../GetBattleDetail` | 单局详情（KDA、英雄、装备等） |
| 昵称查号 | `https://m.wegame.com.cn/api/mobile/lua/proxy/.../query_by_nick` | 昵称→召唤师 id+大区 |

来源依据：CSDN 抓包笔记、GitHub `rainzee/WegameApiReversing` 逆向仓库、第三方"绩查查 API"均指向同一套 WeGame 接口。腾讯新闻亦确认海克斯大乱斗由**腾讯代理运营**。

**关键推论**：
1. hexdata 的"追溯到腾讯 API"大概率指拉取 **WeGame/掌盟战报**（个人战绩）。这意味着它的底层也是这群接口，而非 Riot 全球 API。
2. **这些接口需要本人登录授权（cookie / token）**，是个人账户数据。对个人本地工具而言，拉**自己的**对局做分析合规可行；批量拉他人数据违反 ToS——本项目定位"本地个人分析"，走"分析自己"路线最稳。
3. 国服（腾讯/WeGame）与全球服（Riot Games API）是**两套独立体系**，数据不通。

### 5.3 国服 vs 港澳台（本轮第 1 点）

- **国服（WeGame）**：玩家基数、样本量、娱乐热情都最大，**海克斯大乱斗参考价值的绝对主力**，优先做。
- **港澳台（Garena TW / 台服）**：人口与玩家规模远小于国服，样本稀疏；若做跨服对比，需单独建 Garena 数据管道（与 WeGame 不同基础设施）。
- **外服**：走 Riot Games API（developer.riotgames.com），但**该 API 不覆盖中国区**；且海克斯大乱斗在部分外服可能命名/上线节奏不同。跨服对比属可选项，优先级最低。

### 5.4 hexdata 为 AI 开放的两个端点（保留，硬约束）

`robots.txt` 明确 `Allow: /data/ai-summary.json` 与 `Allow: /api/hexdata/answer-cards`，并为 GPTBot/ClaudeBot 等单独开权限。实测 `ai-summary.json`（54KB）含 topHeroes(12)/topAugments(12)/heroAliases(172)/methodology/citationPolicy。

**使用边界（务必遵守）**：检索式获取 ✅；独立模型训练 ❌；批量转载 ❌；商用 ❌。引用须附「数据来源：Hexdata」+ canonical 链接 + **buildId + reportPatch + reportDate**。

### 5.5 数据策略建议（结合本地优先）

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 借 hexdata 公开 JSON | 零采集、质量高、每日更新 | 起步最快，受许可约束（标注、非商用） |
| B. 自采 WeGame API | 完全自主、可分析自己 | 需本人 token；个人对局样本量有限，做聚合统计不够 |
| **C. 混合（推荐）** | 元数据走 Data Dragon+CommunityDragon（自由）；聚合统计先借 A；个人维度（分段/英雄技能组）走 B 自采 | 兼顾速度与合规 |

## 六、模式机制：隐藏分 / MMR、地图、英雄技能组（本轮第 1、3 点）

### 6.1 玩家隐藏分 / MMR（用户猜测属实，可落地）

- **海克斯大乱斗有独立隐藏 MMR**，且"参考极地大乱斗的隐藏分，但不是简单对应关系"——初期偏低，场次越多越准（腾讯新闻原话）。**模式没有排位分数**。
- 第三方站（whatismymmr.com）用公开对局数据建模估算。Riot 不公开数值。
- **用户第 1 点"从数据水平给玩家赋值"完全可行**：拿个人对局日志（胜/负 + 对手强度），用 ELO 更新公式反推每位玩家 rating：

```python
# 简化 ELO/MMR 更新（已在 CSDN 笔记中验证思路）
def update_mmr(p, opp_avg, result, k=32):
    exp = 1 / (1 + 10 ** ((opp_avg - p) / 400))
    return round(p + k * (result - exp), 1)
```

- 这正是 hexdata「海斗查分」模块的雏形逻辑。**本项目可在本地对个人对局做 MMR 估计，再把玩家分层（如 前20%/前40%/全量）作为分析切片**——与 §1.3 的"玩家分段"维度对接。

### 6.2 地图维度（用户说"三张地图"，需澄清）

- **海克斯大乱斗当前仅存在于「嚎哭深渊」一张图**（官方：限时模式上线时"只存在于嚎哭深渊"）。
- 用户说的"三张地图"应是**极地大乱斗（ARAM 家族）的整体轮换**：嚎哭深渊 / 屠夫之桥 / 灵魂莲华 / 进步之桥（现共 4 张，其中灵魂莲华、屠夫之桥已常驻）。
- **结论**：对海克斯大乱斗本身，地图目前是常量（1 张），不必现在重投入；但**把它作为预留维度**——一旦该模式扩展到其他地图，架构要能加 `map` 字段。不要为了"三张地图"现在就过度设计。

### 6.3 英雄技能组集成（用户第 3 点）

- 每位英雄有 Q/W/E/R + 被动，决定其在海克斯大乱斗的定位（Poke / 坦克 / 爆发 / 续航 / 机动）。
- **做法**：用 Data Dragon 的英雄技能描述，给每个英雄打"技能原型标签"（range / AoE / CC / sustain / mobility / burst），做成静态标注表。
- 价值：把"英雄技能组"这个定性维度量化，与"强化符文路线"做交叉分析（如：高 Poke 英雄配哪类 Augment 胜率最高）。这是比单纯看胜率更深一层的分析，且**不需要对局数据**就能先建起来。

## 七、本地优先与模型本地构建（本轮第 2 点）

用户明确：早期是**本地运行的软件，不是上线的网站**；模型在本地构建。

**架构取向**：
- 不建公网服务、不做账号系统、不做实时查库。
- 数据在本地落库（SQLite / DuckDB / Parquet），统计与建模在本地跑（Python 脚本或本地 FastAPI）。
- 界面是**本地桌面应用**，打开即用，数据可离线。
- 这与 resg 的"数据即 ES module + Service Worker"思路一致（零后端、可离线），但更进一步：连分析都在本地，不依赖任何远端计算。

**对技术栈的含义**：界面层与数据层都要能在 Windows 单机跑通，优先选用户已掌握的技术。

## 八、语言与本地编程储备可行性（本轮第 4 点）

用户是 **Flutter / Windows 桌面开发**为主，兼 **Python 生态**（Mangrove 用 Python 工具），参考实现用过 **Qt**。

### 推荐技术栈（本地优先 + 用户储备匹配）

| 层 | 选型 | 可行性 | 理由 |
|---|---|---|---|
| **界面壳** | **Flutter Desktop（Windows）** | ✅ 高 | 用户主技能；Flutter 3.x Windows 已稳定 |
| **数据层** | **Python**（pandas / polars / duckdb） | ✅ 高 | 用户已用 Python 做 Mangrove 工具；ETL/统计成熟 |
| **统计/建模** | Python（scipy / numpy / ELO 自写） | ✅ 高 | Wilson 区间、ELO/MMR、聚类都在 Python 生态 |
| **可视化** | **ECharts**（见 §九） | ✅ 高 | Apache-2.0， richest 图表库 |
| **界面↔数据桥** | Flutter 调本地 Python（subprocess / 本地 FastAPI） | ✅ 中 | 常见模式，Mangrove 已验证 headless 调用 |

**结论**：用户本机储备完全够用。最自然的组合是 **Flutter Desktop 做壳 + Python 做数据与统计 + ECharts 做图**。纯 Python（PySide6 + QWebEngine + ECharts）也可，但偏离用户主技能，不优先。

## 九、专业数据分析工具与可视化技术（本轮第 5、6 点）

### 9.1 重要修正：GitHub 上的 LOL 项目大多不适用国服

用户第 5 点想找"lol/海克斯相关标签的数据分析项目"。实测：
- LOL 数据分析 Python 项目几乎全是 ★0–17 的 Jupyter Notebook，且针对**全球服**。
- `cassiopeia` / `Riot-Watcher`（MIT）封装的是 **Riot Games 全球 API**，**不覆盖中国区**（腾讯独立运营）。
- **结论**：这些项目只能借鉴"方法论/代码模式"（ELO 估算、Wilson 区间、EDA 笔记本），**不能直接用于国服数据获取**。国服数据必须走 §五 的 WeGame 接口 + 自采。

### 9.2 真正该借的"专业工具"是通用 Python 数据栈

| 工具 | 用途 | 许可 |

| scipy / numpy | Wilson 区间、ELO/MMR、统计检验 | BSD |
| pyecharts | **Python 里画 ECharts 图** | MIT |

### 9.3 可视化技术选型（用户第 6 点：DataEase / cola-designer / makeapie）

**核心结论：这三家最终都靠 ECharts 渲染图表。** 所以真正要吸收的是 **Apache ECharts**，其余是"思路借鉴"：

| 项目 | 真实定位 | 许可 | 可借鉴点 | 警告 |
|---|---|---|---|---|

## 十、UI 地基与借鉴思路（本轮第 7 点）

用户：借鉴两站思路，但自己创建可打开的界面；若 0 开发困难，找可借用的 UI 地基。

### 10.1 "借思路不抄界面"是原则
