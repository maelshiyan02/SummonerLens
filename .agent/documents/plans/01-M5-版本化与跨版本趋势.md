# M5 · 版本化与跨版本趋势（专项规划 v1）

> 状态：**规划完成，待开工**。上级：`00-项目计划书.md` §四 M5。
> 前置：M0–M4 已完成（M4 仅剩用户本地构建验证，见 §6）。
> 依据：本文件所有"现状"均为 2026-10-11 实测（脚本/目录/线上接口），非推测。

---

## 1. 目标

让每一份数据**可溯源到具体版本**、**可跨版本对比**、**变更可自动追踪**。
一句话：把「数据是几号的、和上个版本比变了什么」变成工具里可回答的问题。

---

## 2. 现状盘点（实测）

| 对象 | 现状 | 结论 |
|---|---|---|
| 元数据快照 `data/meta/<ver>/` | **16.19.1 / 16.20.1 两版并存** | ✅ 已有真实多版本 |
| 元数据 diff | `tools/check_version_changes.py`（新增/移除/机制数值变更） | ✅ 可用，但**只打印、不入库** |
| 聚合快照 `data/agg/<buildId>/` | **仅 1 份**：`hexdata-2026-09-27-f9b948bc5ff0` | ⚠️ 无第二份 |
| 聚合多快照机制 | `fetch_hexdata.py` 按 buildId 建目录 + `LATEST` 指针 | ✅ **机制已具备**，缺的是积累 |
| 线上数据是否更新 | 实测 `buildId` 与本地**完全一致**；`patchComparison.hasComparison=False`、`previousPatch` 空、`risingHeroes/fallingHeroes` **均为空** | 🔴 **无现成趋势数据可白拿** |
| 落库溯源字段 | 每表 `_source/_confidence/_asof/_collected_at` | ✅ 已贯穿（M2） |
| 前端 | 无版本维度、无溯源展示、无趋势图 | ⚠️ 待建 |
| 自动化 | 无（hexdata 靠手动跑） | ⚠️ 待建 |

### 🔴 最关键的现实约束

**真实聚合趋势无法立刻得到**：
- hexdata 的 `buildId` 目前未更新（与本地同一份），且其 `patchComparison` 为空；
- ⇒ **趋势的真实数据点只能靠"线上更新时抓一份"逐步积累**。

**应对（三条腿走路，缺一不可）**：
1. **元数据侧立刻做真的**：`16.19.1 → 16.20.1` 的真实 diff 现在就能算能看；
2. **聚合侧先把机制和界面建好**，用**明确标注 `synthetic` 的多版本序列**做开发与验收（承 M4 的 `synthetic_fixture` 分区纪律），真实数据一到即替换；
3. **建自动化定时抓取**，让积累自动发生（而不是靠人记得）。

## 3. 范围（做什么）

### 3.1 版本注册表
- 新增 `data/versions.json`（随仓）：汇总所有快照的 `{kind: meta|agg, id, patch, date, collected_at, path, is_latest}`。
- 新增 `python/etl/build_versions_index.py`：扫描 `data/meta/` 与 `data/agg/` 生成/刷新注册表（幂等）。
- 意义：前端与跨版本内核**只读这一份**，不再各自猜目录。

### 3.2 跨版本对比内核
- 新增 `python/stats/trend.py`：
  - `diff_meta(old_ver, new_ver)` → 英雄/装备 新增·移除·机制数值变更（把 `check_version_changes.py` 的签名逻辑**升级为可复用函数 + 结构化输出**）；
  - `diff_agg(old_bid, new_bid)` → 同实体（英雄/符文）胜率·pick 变化与升降排序；
  - **快照不足时必须显式返回 `insufficient_snapshots`（不得返回空表冒充成功）**——承 kb M01（空结果判 FAIL）。
- `check_version_changes.py` 改为**薄壳**调用 `trend.diff_meta`，保持命令行兼容。

### 3.3 落库跨版本
- `build_duckdb.py` 增表：
  - `agg_top_heroes_history` / `agg_top_augments_history`（含 `_asof` = buildId，多快照并存）
  - `meta_champion_changes`（跨版本英雄改动）
- 增视图 `v_hero_trend`（英雄 × 版本 序列，供趋势查询）。
- 每表继续强制四列溯源，`verify_pipeline.py` 补断言。

### 3.4 前端（`app/web`）
- **版本选择器**：读 `versions.json`，切换 `?ver=` 深链（与既有 `?tab=&dataset=&entity=&tier=&q=` 并存）。
- **新视图「版本变更」**：
  - 元数据：本版新增/移除英雄装备、机制数值变动的清单（真实数据）；
  - 聚合：英雄胜率升降榜（有 ≥2 快照时；不足时显示"数据积累中（当前 1/2）"而非空图）。
- **趋势折线**：多英雄胜率历史（≥2 快照才绘制）。
- **溯源角标（全局）**：右上角常驻 `buildId / patch / reportDate / 数据来源：Hexdata`（合规硬要求，A13 §3）。
- 顺带接入**已抓但未展示**的 hexdata 维度：`economyRanking` / `riskNotes`（M2 已存 `methodology.json`，零新增抓取成本）。

### 3.5 自动化积累
- 新增 `tools/sync_snapshots.py`：抓 hexdata（+ 可选 Data Dragon）→ 检测 `buildId`/版本是否变化 → 有变化则落快照、刷新注册表、产出变更报告。
- 挂 **WorkBuddy 定时任务**（每日一次）：静默运行，有变更时给出简报。
- 变更报告落 `data/derived/changes/<date>.md`（派生、gitignore）。

### 3.6 验收与记忆
- 新增 `tools/verify_m5.py`：正向全绿 + `--self-test` 故障注入真变红（承 M01/M11 纪律）。
- 新增附录 **A16**（版本化与趋势）、日志 **W10**；更新计划书 M5 与 `W00` 索引。

## 4. 明确不做（避免范围蔓延）

- **港澳台 / 外服管道**：计划书标为最低优先级；用户为国服玩家 ⇒ **本阶段不做**，仅在数据模型预留 `server` 字段（默认 `cn`）。
- 不追求"补抓历史版本"：hexdata 不提供历史快照，**不做**任何逆向/伪造历史数据的尝试。
- 不引入新依赖（继续标准库 + duckdb）。

---

## 5. 验收标准

| 项 | 判据 |
|---|---|
| 版本注册表 | `data/versions.json` 覆盖全部 meta/agg 快照，字段完整 |
| 元数据真实 diff | `16.19.1 → 16.20.1` 输出英雄/装备改动清单，**非空且可复算** |
| 聚合 diff 边界 | 仅 1 份快照时**返回 `insufficient_snapshots`**，前端显示"积累中"而非空图 |
| 落库 | 2 张 history 表 + `v_hero_trend` 视图存在；四列溯源无空值 |
| 前端 | `?ver=` 深链可切换；版本变更视图渲染；溯源角标可见 |
| 自动化 | 定时任务实跑 `LastTaskResult=0`，无变更时静默、有变更时出报告 |
| 反向验证 | `verify_m5.py` 正向 0 失败；`--self-test` 注入断言**真变红** |
