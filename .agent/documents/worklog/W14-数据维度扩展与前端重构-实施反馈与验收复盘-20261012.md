## 2. 第二轮 Commit（8ffb8f1）：修补过程实录

### 2.1 Bug #1 —— `load_resg_rankings` ver 参数被内部变量覆盖

**现象**：
- `build_viz_bundle.py` 里 `load_resg_rankings(root, hero_meta, aug_meta, ver)` 函数签名加了 `ver` 参数
- 函数内部第一行 `ver = latest.read_text(encoding="utf-8").strip()` —— 这是 RESG 快照的版本号（16.20）
- 但函数参数 `ver` 在调用时传入的是 **meta 版本号（16.20.1）**
- 两者不一致：items_modes.csv 在 `data/meta/16.20.1/` 下，而覆盖后的 ver 变成 16.20，路径 `data/meta/16.20/items_modes.csv` 不存在 → 走到 else 分支

**调试过程**（关键转折点）：

第一次调试：直接在外部模拟路径拼接 → exists=True，rows=870
```python
item_fp = root / "data" / "meta" / ver / "items_modes.csv"
print(f'ver={ver}')           # ver=16.20.1 ✅ 对的
print(f'exists={item_fp.exists()}')  # True ✅
```

第二次调试：直接调 `load_resg_rankings` → items kind=unavailable，rows=0
```python
result = load_resg_rankings(root, hero_meta, aug_meta, ver)
print(result["resg_items"])   # kind=unavailable, rows=0 ❌
```

第三次调试：在函数内部加 print
```python
print(f"[DEBUG load_resg_rankings] ver={ver}")
# 输出: [DEBUG load_resg_rankings] ver=16.20  ← 变了！
```

**根因**：函数内 `L626 ver = latest.read_text()` 覆盖了函数参数。

**修复**：内部变量改名为 `resg_ver`，函数参数 `ver` 保留给 items_modes.csv 路径。

```python
# 修复前
ver = latest.read_text(encoding="utf-8").strip()
rdir = resg_root / ver

# 修复后
resg_ver = latest.read_text(encoding="utf-8").strip()
rdir = resg_root / resg_ver
```

**为什么会犯这个坑？**
- 函数签名里的参数名和内部临时变量同名，是典型的「参数遮蔽」（parameter shadowing）
- 加参数时只看了前半段代码（英雄/海克斯读取），没注意后半段（items）也用到了 ver
- 构建日志只打印了 kind 和 rows 数量，else 分支的 unavailable 被当作正常情况接受了

### 2.2 Bug #2 —— kind 白名单需要同步扩展

items 修好后 kind 变成 `real_metadata`，此时 verify_m4 和 test_m4_unit.js 都报错：

```
verify_m4.py L182: 所有数据集 kind 取值合法 → FAIL
test_m4_unit.js L222: ['real_aggregate', 'real_aggregate_resg', 'synthetic_fixture', 'unavailable']
```

**修复**：两处白名单都扩 `real_metadata` + `real_versioned`：
```python
# verify_m4.py
("real_aggregate", "real_aggregate_resg", "real_metadata", "real_versioned",
 "synthetic_fixture", "unavailable")

# test_m4_unit.js
['real_aggregate', 'real_aggregate_resg', 'real_metadata', 'real_versioned',
 'synthetic_fixture', 'unavailable']
```

**经验教训**：每新增一个 kind 值，必须同步检查所有 kind 断言的白名单。这类字符串匹配很容易漏。

### 2.3 verify_resg.py —— 独立验收脚本

第一轮提交后没有 RESG 专项验收脚本，这违反了项目「每个已完成需有持久化验收脚本」的纪律。

第二轮补充创建 `tools/verify_resg.py`，覆盖三层验证：

| 层 | 验证点 |
|----|--------|
| 原始文件 | 英雄 ≥150 / 海克斯 ≥180 / citation 四字段 / wr 与 wm/tm 抽样一致（30 条） |
| DuckDB | 表存在 / 溯源列无空值 / 行数达标 / _confidence=aggregate_resg |
| 数据束 | 三数据集存在 / kind 正确 / rows ≥ 下限 |

**--self-test 故障注入**：
- 注入方式：临时改 min_ch=10、min_aug=10、改 kind 期望值为 WRONG
- 退出码逻辑：注入后应该有 FAIL → `退出码 1` = 注入生效；如果全绿 → 注入没生效
- 实测结果：`ExitCode=1 ✅`

**退出码反转踩过的坑**：
第一次写 self-test 退出码时，写成了：
```python
sys.exit(0 if not all_ok else 1)  # 反了！
```
正确应该是：
```python
sys.exit(1 if not all_ok else 0)  # 有 FAIL → 退出码 1
```
第二次修正后才对。这类「真/假反转」逻辑极其容易写反，写完后必须立即跑一遍验证。

## 4. 经验教训（按类别整理）

### 4.1 参数遮蔽（Parameter Shadowing）

| 教训 | 说明 |
|------|------|
| **函数内重新赋值函数参数是高风险模式** | `load_resg_rankings` 里 `ver = latest.read_text()` 覆盖了调用方传入的 `ver`，导致 items_modes.csv 路径拼接用了错误的版本号 |
| **调试时优先加 print 看参数值** | 第一次在外部模拟路径对、函数内部不对，加 print 立刻看到 ver 从 16.20.1 变成了 16.20 |
| **修复用重命名而非删除覆盖** | 把内部临时变量改名为 `resg_ver`，保留参数名不动——因为调用方依赖参数名 |

### 4.2 Kind 白名单同步

| 教训 | 说明 |
|------|------|
| **字符串白名单是隐性耦合点** | verify_m4 / test_m4_unit / build_viz_bundle 三处都有 kind 白名单，改一处容易漏另外两处 |
| **建议：把 kind 常量集中定义** | 未来可在 `python/stats/constants.py` 或前端 `core.js` 里定义 `KIND_WHITELIST`，各脚本 import 使用 |
| **构建日志的 kind 列只打印不校验** | 构建日志里 `resg_items 0 行 [unavailable]` 没被当异常，但实际上 items_modes.csv 存在——构建脚本自己应该断言 `kind != "unavailable"` 且文件存在时 rows > 0 |

### 4.3 故障注入退出码

| 教训 | 说明 |
|------|------|
| **退出码反转逻辑极易写错** | `sys.exit(1 if not all_ok else 0)` 和 `sys.exit(0 if not all_ok else 1)` 肉眼看不出区别 |
| **写完 self-test 后必须立即跑** | 写的时候自以为逻辑对，跑出来全绿（退出码 0）才发现反了 |
| **推荐写法** | 把 self-test 退出码逻辑包成 `_self_test_exit(all_ok)` 函数，加注释说明「注入后 FAIL 才算真变红」 |

### 4.4 工程交付纪律

| 教训 | 说明 |
|------|------|
| **不要相信「看起来全绿」** | 第一轮 verify_pipeline 68/0 + verify_m4 92/0 全绿，但 items_modes 没接上、独立验收脚本没写——绿的是**已有断言覆盖的部分**，没覆盖的部分仍然是盲区 |
| **Advisor 检查必须跑** | 提交后 Advisor 的三个收尾缺口点得准，避免了把半成品推上去 |
| **临时调试脚本必须清理** | 过程中创建了 `_tmp_inspect_items.py`、`_tmp_debug.py`，后来手动删除——未来可以在 git pre-commit hook 里加规则阻止 `_tmp_*` 提交 |

### 4.5 数据缺口的正确处理

| 教训 | 说明 |
|------|------|
| **如实报告 > 硬填假数据** | RESG/hexdata 均无装备聚合端点时，不要编造 wr=0.5 的假数据 |
| **元数据是「真实可用的次优选择」** | 没有聚合胜率时，展示已有的 870 件装备元数据（价格/分类/模式归属）比空白好得多 |
