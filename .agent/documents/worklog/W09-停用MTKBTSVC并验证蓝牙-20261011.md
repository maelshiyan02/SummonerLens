# W09 · 停用 MTKBTSVC 并验证蓝牙（根治方案②）

- **日期**：2026-10-11
- **类型**：运维处置（非里程碑）
- **前置**：W08 末尾发现本机 `mtkbtsvc.exe`（MediaTek 蓝牙服务）持续句柄泄漏；已落地看门狗（方案① 的替代）。本文记录用户选定 **方案② 停用服务** 的执行与验证。
- **相关**：`.agent/memory/2026-10-11.md`「本机故障调查：mtkbtsvc 句柄泄漏」；工具 `tools/bt_handle_guard.ps1`；跨项目事实见用户级 MEMORY.md。

## 0. 决策与风险窗口

- 泄漏根因在厂商用户态服务自身（驱动 1.1044.0.556 已是现网最新，无法靠"更新驱动"解决）。
- 方案② = **停用 `MTKBTSVC`**：最彻底且可逆，唯一风险是"蓝牙是否还能用"。
- **停用前实况（关键）**：三个已配对外设 **TWS / K18 / BS17 全部离线**（`present=False`），无任何蓝牙设备在用 ⇒ **零打扰窗口**。

## 2. 关键判别实验：蓝牙是否依赖 MTKBTSVC

停用后 Windows 报 `BT radio: 蓝牙 = Off`。但 **Off 有两种可能**（本来就关 / 服务停用导致不可用），而停用前未留 radio 基线 ⇒ 必须做对照实验定性。

用 **WinRT Radio API** 在**停用状态下**尝试驱动无线电：

`tools/bt_handle_guard.ps1 -Action radio`（新增动作，只读）

```
radios reported total=2
  radio: kind=Bluetooth state=Off name=蓝牙
  radio: kind=WiFi      state=On  name=WLAN
BT radio BEFORE: state=Off
RequestAccessAsync -> Allowed
SetStateAsync(ON)  -> Allowed
BT radio AFTER ON attempt: state=On
VERDICT: radio is drivable WITHOUT mtkbtsvc -> BT stack OK
```

**结论**：即使 `MTKBTSVC` 完全停用，Windows 蓝牙无线电仍可被正常驱动（Off → On 成功）。
⇒ 蓝牙可用性由 **`bthserv` + `BTHUSB`/`BTHPORT` + MTK 过滤器驱动（`MTKBTFilterx64`，Running）** 提供，**与厂商用户态服务无关**。方案② 成立。

> 附带确认：`WiFi=On` 且能被枚举，说明 Radio Manager 本身健康；`MTKBTSVC` 停用未波及其它无线电。

## 4. 回滚与后续

- **一键回滚**：`tools/bt_handle_guard.ps1 -Action enable`
  → `StartupType=Automatic` + 启动服务，**并自动重新启用**看门狗计划任务（本次已把这两步合并进脚本）。
- **日常健康检查**：`-Action radio`（只读）随时确认蓝牙无线电是否仍在。
- **看门狗现状**：计划任务保持 **Disabled**（服务已停用，无守护对象）。若回滚服务，`enable` 会一并恢复它。
- **保持状态**：本次为便于用户实测，蓝牙开关已置于 **On** 并保持；如需关闭可在 Windows 快速设置中关闭（与 `MTKBTSVC` 无关）。
- **待用户实测**：用 TWS / K18 / BS17 实际连接一次，确认音频/HID 链路在无厂商服务下正常（本次无设备在线，Agent 侧无法完成真实连接验证）。

## 5. 沉淀

- `tools/bt_handle_guard.ps1` 增 `radio` 动作；`disable`/`enable` 联动看门狗任务；`watch` 在服务已 Disabled 时直接退出（不再无意义轮询）。
- 方法论：**"是 A 导致还是本来就如此"必须用对照实验回答**——本例中"停用后 radio=Off"不能直接归因于停用，须在停用状态下尝试驱动以定性。
